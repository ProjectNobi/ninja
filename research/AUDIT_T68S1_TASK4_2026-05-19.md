## t68s1-gold

### Root Cause of Timeouts

**Primary cause: FEATURE_BUILD tasks generate large context + long patches; T68-S1's 32768-token limit causes OOM-induced latency spikes or hard timeouts at the GPU/vLLM level.**

Three compounding factors:
1. **Wrong endpoint in script**: `multi_model_sampler.py` had `base_url = "http://100.69.88.107:8080/v1"` (direct Tailscale IP). The socat proxy at `localhost:8082` has better connection management. Fixed to `localhost:8082`.
2. **max_retries = 5 for all providers**: Each failed t68s1 task wasted 5 × (1+2+4+8+15s backoff) ≈ **466 seconds**. With ~25% failure rate on FEATURE_BUILD tasks, ~25% of total runtime was pure waste.
3. **timeout = 300s**: T68-S1 reliably completes within 90s on successful tasks (measured: 13s–88s for simple/medium tasks). A 300s timeout means a stuck/OOM task holds a worker slot for 5 minutes before being released.

**vLLM health check**: Both endpoints responding correctly. Model `qwen3-30b-awq` serving with 32768 max_len. Generation test: 131-line patch in 14.5s. No issues with the server itself — purely a load/task-complexity issue.

### Output File Status

**Previous run output was LOST.** The script ran from `~/backups/github-staging/sn66-ninja/` directory. Despite `OUTPUT_DIR = Path("/root/sn66-ninja/training_data/gold_patches")` in the script, the process was interrupted at task 1039/9122 and the file `gold_patches_qwen3-30b-awq.jsonl` does not exist in any location on Hetzner1 or AnonServer. 

Likely cause: An earlier run did exist (tmux showed `Tasks: 0/9122 done` → the script found no existing file, but the display counter was confused by cached terminal scrollback showing [1007/9122] from a **different concurrent run** that was saving to the same file but from the backup dir. Both processes may have been writing to the same output path and corrupted/deleted each other's work.

### Fixes Applied

1. **Script location**: Deployed fixed `multi_model_sampler.py` to `/root/sn66-ninja/` (canonical location)
2. **Endpoint fix**: `http://100.69.88.107:8080/v1` → `http://localhost:8082/v1` (Hetzner1 socat proxy)
3. **Retry reduction**: `max_retries = 2 if provider == "t68s1" else 5` — fails fast, moves to next task
4. **Timeout**: Restarted with `--timeout 90` (90s per attempt vs 300s)
5. **Workers**: `--workers 2` (parallel generation to recover time)

### Restart Command Used
```bash
cd /root/sn66-ninja && python3 multi_model_sampler.py \
  --model qwen3-30b-awq \
  --provider t68s1 \
  --output-file gold_patches_qwen3-30b-awq.jsonl \
  --timeout 90 \
  --workers 2
```

### Expected Impact

**Before fix**: ~466s per failed task × ~25% failure rate = avg ~117s of waste per task  
**After fix**: ~(90+1+90) = ~181s per failed task × ~25% = avg ~45s of waste per task  
**Per-task average time improvement**: ~72s saved per task on failures  
**New ETA**: Observed ~90h for first 4 tasks (ETA stabilizing as more data accumulates). With 2 workers, effective throughput ≈ 2× per wall-clock hour. Realistic estimate: **40–50h to complete** vs original 124h.

### Remaining Issues

- Tasks are starting fresh (0/9122) — the ~1039 previously completed records were lost. Accept the ~8h sunk cost and run clean.  
- `--workers 2` adds concurrent load on T68-S1. Monitor for degraded latency. If ETA climbs above 80h, reduce to `--workers 1`.
- When T68-S2 arrives (NVLinked, 242GB unified RAM), consider migrating the run there with `--workers 4` for much faster throughput.
